# 통신 프로토콜 명세서 (신규)

문서 버전: 1.0 / 개정일: 2026-09-10
과제 요구사항 3.2.4 "길이 접두사 방식의 TCP 메시지 경계 처리와 JSON 요청·응답 규격"에 대응한다.

## 1. 전송 계층
- TCP/IP 소켓, 클라이언트가 서버에 접속(서버는 리스닝 포트에서 `Accept` 대기).
- 하나의 TCP 연결 = 하나의 세션. 로그인·현장 검사·이력 조회 모두 같은 연결로 처리한다(연결당 하나의 상태 머신 인스턴스).
- 연결이 끊기면 서버는 해당 세션의 진행 중 검사를 즉시 취소하고(저장 안 함) 세션 자원을 정리한다. 재연결은 새 세션으로 간주하며 이전 상태를 복구하지 않는다.
- 서버는 다중 클라이언트 접속을 지원한다(연결마다 독립 스레드/Task + 상태 머신 인스턴스).

## 2. 메시지 프레이밍
모든 메시지는 다음 봉투로 감싼다.

```
[4 bytes] PayloadLength   (Int32, Big-Endian, 헤더 제외 페이로드 바이트 수)
[1 byte]  MessageType     (0x01 = JSON 제어 메시지, 0x02 = 이미지 프레임)
[N bytes] Payload
```

- **0x01 JSON 제어 메시지**: UTF-8 인코딩된 JSON 문자열. 요청·응답·상태 전이·안내 문구·판정 결과·이력 조회 등 이미지 바이트를 제외한 모든 통신에 사용한다.
- **0x02 이미지 프레임**: JPEG로 압축된 raw 바이트. Base64 인코딩하지 않는다(오버헤드 회피). 클라이언트→서버(웹캠 프레임), 서버→클라이언트(결과 대표 이미지, 이력 상세 이미지) 양방향에 사용하며, 프레임 앞뒤로 어떤 요청/응답에 속하는지는 별도 0x01 메시지의 상관관계 ID로 짝짓는다(§4).
- 수신 측은 4바이트 길이를 먼저 읽어 페이로드 크기를 알고, 그만큼 정확히 읽은 뒤 다음 메시지 헤더를 읽는다. 페이로드 중간에 메시지 경계를 임의로 나누지 않는다.

## 3. JSON 메시지 공통 필드
모든 0x01 메시지는 다음 공통 필드를 갖는다.

```json
{
  "type": "LoginRequest",
  "correlationId": "3f2a...(GUID)",
  "payload": { }
}
```
- `type`: 메시지 종류 문자열 (Protocol 프로젝트의 상수로 정의, 클라이언트·서버 공유).
- `correlationId`: 요청-응답 짝짓기용 GUID. 클라이언트가 요청 시 생성하고, 서버는 같은 값으로 응답한다. 서버가 능동적으로 보내는 상태 전이 알림(요청 없이 서버가 주도)은 `correlationId`를 세션의 현재 검사 컨텍스트 ID로 채운다.
- `payload`: 메시지별 DTO. 상세는 §5.

## 4. 이미지 프레임과 JSON의 상관관계
- 클라이언트 → 서버 웹캠 프레임: 0x02 프레임 직전에 0x01 `FrameMeta` 메시지(캡처 시각, 프레임 시퀀스 번호, 해상도)를 보낸다. 서버는 `FrameMeta.correlationId`로 바로 뒤따르는 0x02 페이로드를 매칭한다.
- 서버 → 클라이언트 결과 이미지: 0x01 `InspectionResult` 메시지에 `imageAvailable: true`와 `correlationId`를 담아 먼저 보내고, 곧바로 같은 `correlationId`를 가진 0x02 프레임을 전송한다.
- 항상 "0x01 메타 → 0x02 데이터" 순서를 지킨다. 순서가 바뀌면 상대는 프로토콜 오류로 연결을 종료한다.

## 5. 메시지 카탈로그 (요약)
| type | 방향 | 용도 |
|---|---|---|
| `LoginRequest` / `LoginResponse` | C→S / S→C | 로그인 |
| `LogoutRequest` / `LogoutResponse` | C→S / S→C | 로그아웃, 진행 중 검사 취소 |
| `DashboardStatsRequest` / `DashboardStatsResponse` | C→S / S→C | 대시보드 KPI·차트·최근 10건 |
| `InspectionSessionStart` / `InspectionSessionStarted` | C→S / S→C | 현장 검사 화면 진입, 세션 등록 |
| `FrameMeta` + (0x02 프레임) | C→S | 웹캠 프레임 전송(초당 최대 6회) |
| `InspectionStateChanged` | S→C | WAITING/PERSON_DETECTED/INSPECTING/RESULT 전이, 안내 문구 |
| `InspectionResult` + (0x02 프레임, 조건부) | S→C | 검사 완료, 장비 3종 상태·Score·최종 결과·대표 이미지 |
| `RetryInspectionRequest` / (재검사는 `InspectionStateChanged`로 반영) | C→S | 재검사 요청 |
| `SaveResultAck` | S→C | 저장 성공/`SAVE_FAILED`/저장 중 |
| `RetrySaveRequest` | C→S | 저장 재시도 요청 (같은 InspectionKey) |
| `InspectionSessionEnd` | C→S | 현장 검사 화면 이탈, 카메라 해제 요청 |
| `HistoryPageRequest` / `HistoryPageResponse` | C→S / S→C | 검사 이력 페이지 조회 |
| `InspectionDetailRequest` / `InspectionDetailResponse` + (0x02 프레임, 조건부) | C→S / S→C | 이력 상세(이미지 포함) |
| `ErrorNotification` | S→C | 모델/카메라/추론/DB/서버 내부 오류 안내 |

- 각 DTO의 정확한 필드는 `SafetyVision.Protocol` 프로젝트의 C# 레코드로 정의하며, 이 문서의 표는 목록 수준 요약이다. 구현 시 DTO 필드가 여기 표보다 우선한다.

## 6. 오류·예외 처리
- **잘못된 입력**: 서버는 요청 DTO 검증 실패 시 `ErrorNotification(code: "INVALID_REQUEST")`를 응답하고 연결은 유지한다.
- **인증 전 요청**: 로그인 성공 전에는 `LoginRequest`만 허용한다. 그 외 요청은 `ErrorNotification(code: "UNAUTHORIZED")`로 거절하며, `FrameMeta`처럼 뒤에 이미지 프레임이 오는 요청은 이미지 프레임을 먼저 소비해 TCP 스트림 정렬을 유지한다.
- **연결 실패**: 클라이언트는 접속 실패·타임아웃 시 `서버 연결이 끊겼습니다. 다시 로그인해 주세요.`를 표시하고, 기존 인증을 재사용하지 않은 채 로그인 화면으로 복귀한다.
- **추론 실패**: 서버는 `ErrorNotification(code: "INFERENCE_ERROR")`를 보내고 해당 세션의 검사를 취소한다. 다른 세션에는 영향 없음.
- **DB 오류**: 저장 시점 오류는 `SaveResultAck(status: "SAVE_FAILED")`로 응답한다. 서버 시작 시 DB 연결 자체가 안 되면 서버는 신규 클라이언트 연결(Accept)을 거부한다.
- **카메라 오류**: 클라이언트가 감지해 `ErrorNotification` 없이 로컬에서 안내 문구를 표시하고, 서버에는 `InspectionSessionEnd`(사유: 카메라 오류)를 보내 세션을 정리한다.

## 7. 성능·동시성
- 클라이언트 웹캠 프레임 전송: 초당 최대 6회, JPEG 압축(초기 품질 80). 미리보기(로컬 렌더링)와 전송 샘플링은 별도 스레드/파이프라인으로 분리해 네트워크 지연이 미리보기 프레임률에 영향을 주지 않게 한다.
- 클라이언트는 전송 중인 프레임 1개와 최신 대기 프레임 1개만 유지해 네트워크 지연 시 큐가 무한히 늘어나지 않게 한다. 서버는 세션별 `MaxInferenceFps`와 프레임 시퀀스를 확인해 오래된·중복 프레임을 폐기한다.
- 세션당 최대 1개의 추론이 동시 실행된다. 여러 세션의 추론은 서버 프로세스 내에서 순차 또는 제한된 병렬(추론 세마포어)로 처리하며, 목표 처리량은 발표 PC 실측 후 README에 기록한다.

## 8. 보안 범위
- 이 프로젝트 범위에서 TLS/암호화 채널은 필수 구현 대상이 아니다(사내망/로컬 시연 전제). 필요 시 이후 TLS 소켓으로 교체 가능하도록 Protocol 계층을 소켓 스트림 추상화 위에 구현한다.
- 로그인 비밀번호는 평문으로 로그에 남기지 않는다. JSON payload에는 포함되지만 서버 로그·콘솔 출력에는 마스킹한다.

## 9. 최종 통합본 추가 메시지

관리 화면에서 사용하는 메시지는 다음과 같다. 모두 0x01 JSON 제어 메시지이며, 서버는 동일한 `correlationId`로 응답한다.

| type | 방향 | 권한 | 용도 |
|---|---|---|---|
| `StatisticsRequest` / `StatisticsResponse` | C→S / S→C | 로그인 사용자 | 기간별 검사 건수·장비·일/월·카메라 통계 |
| `EquipmentManagementRequest` / `EquipmentManagementResponse` | C→S / S→C | 관리자 | 장비 목록·등록·수정·삭제 |
| `UserListRequest` / `UserListResponse` | C→S / S→C | 관리자 | 사용자 목록 |
| `UserCreateRequest` / `UserMutationResponse` | C→S / S→C | 관리자 | 사용자 등록 |
| `UserPasswordChangeRequest` / `UserMutationResponse` | C→S / S→C | 관리자 | 사용자 비밀번호 변경 |
| `UserDeleteRequest` / `UserMutationResponse` | C→S / S→C | 관리자 | 사용자 삭제 |
| `SystemSettingsRequest` / `SystemSettingsResponse` | C→S / S→C | 관리자 | 서버·DB·모델 상태 조회 |

관리 메시지는 로그인하지 않은 세션에는 `UNAUTHORIZED`, 관리자 계정이 아닌 로그인 세션에는 `FORBIDDEN`으로 거절한다. 관리 기능의 권한 확인은 클라이언트 메뉴 표시만으로 처리하지 않고 서버 세션에서 다시 수행한다.

`StatisticsRequest.payload.fromUtc`는 포함 하한, `toUtc`는 미포함 상한이다. 예를 들어 하루를 조회할 때는 해당 날짜 00:00 UTC부터 다음 날짜 00:00 UTC 직전까지를 요청한다. 클라이언트는 사용자의 현지 날짜를 이 규칙에 맞는 UTC 범위로 변환한다.

최종 구현은 현재 확보된 `safetyvision_v2_640.onnx` PPE 모델을 기준으로 한다. 외부 Person/Mask 분리 모델이 필요한 다른 설정은 모델 파일과 입력 크기가 함께 배포될 때 별도 검증해야 하며, 현재 최종본의 실행 경로에는 포함하지 않는다.
