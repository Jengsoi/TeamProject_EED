# 개발 일정 및 역할

문서 버전: 3.0 / 개정일: 2026-09-10
개정 사유: 클라이언트-서버 구조 반영. 역할 A는 AI+서버 통신 계층까지 포함, C는 MySQL·저장·집계 유지, B는 WPF 클라이언트+TCP 클라이언트 통신.
개발 인원 3명 / 개발 기간 7일. 모델·목업과 확정한 기능 범위를 유지한다.

## 1. 역할
| 담당 | 주 책임 | 공동 연결 지점 |
|---|---|---|
| A — AI/서버 코어 | 모델 준비, ONNX 전후처리, ROI/인원, PPE 연결, 누적 판정, 대표 이미지, **서버 상태 머신·세션 관리** | Core 인터페이스, Protocol DTO, 검사 상태·결과 DTO |
| B — 클라이언트 UI | 로그인, 대시보드, 현장/결과, 이력, 목업 스타일, 안내·버튼 상태, **웹캠 캡처·TCP 클라이언트 통신·재연결 처리** | ViewModel, Protocol DTO, 화면 이동·재검사·저장 상태 |
| C — DB/통합 | **MySQL(Pomelo) EF Core**, 계정 해시/Seed, 검사·이미지 저장, 집계, 페이지 조회, **TCP 서버 리스너·세션 라이프사이클**, 통합 | 저장 DTO, InspectionKey, 오류·중복 방지, 다중 클라이언트 처리 |

- Day 1에 Detection, EquipmentResult, InspectionResult, 그리고 **Protocol 메시지 DTO(§07_통신프로토콜.md)**를 합의한다.
- 좌표는 원본 영상 픽셀, Score는 nullable 0~1, 시각은 UTC로 통일한다.
- 분담 개발용 Fake는 명시적 개발 설정에서만 사용하며 최종 모델 대체 수단으로 사용하지 않는다.
- Protocol 프로젝트(DTO·프레이밍 유틸)는 A/B/C가 공동 소유하며, 변경 시 3명 모두에게 영향이 가므로 Day 1에 최대한 확정한다.

## 2. Day 1 — 실제 모델 연결과 서버/프로토콜 기본 계약
공통:
- Solution/프로젝트(Client/Server/Core/Protocol/Data), Git, NuGet, .NET 10 Windows x64 설정.
- Core 인터페이스/DTO, Protocol 메시지 카탈로그, 서버 설정 파일 초기값, cancellation·검사 식별자 구조 확정.
- Windows `dotnet restore` / `dotnet build` 확인(Client·Server 각각), 패키지 버전 고정.

A:
- v2/best_640.onnx 다운로드·배치, SHA-256·날짜 기록.
- 실제 metadata·클래스·shape 확인, 정지 이미지 추론·좌표 복원 성공(서버 프로세스 내에서).
- 발표 PC에서 워밍업 후 추론 속도, 실제 장비 정면·거리·조명 검출을 먼저 확인.

B: 목업 기반 기본 레이아웃·로그인/대시보드 화면 틀, TCP 클라이언트 연결·프레이밍 유틸 초안.
C: MySQL 스키마 설계·EF Core Migrations, 초기 관리자 Seed, 비밀번호 검증, TCP 서버 리스너 골격(Accept 루프, 세션 등록).

완료 기준: 실제 ONNX 정지 이미지 추론 성공(서버) + 로그인 가능한 MySQL DB + TCP 에코 수준의 클라이언트-서버 연결 확인 + 솔루션 빌드.
모델 연결이 실패하면 원인을 먼저 해결하고, UI Fake 진행을 실제 AI 완성으로 보고하지 않는다.

## 3. Day 2 — 웹캠·프레임 전송·화면 연결
- A: 서버 내 웹캠 프레임 수신·순차 추론, ROI·Person 인원수·크기 확인, 5초 수집량 측정.
- B: 로그인 → 대시보드 → 현장 검사, 웹캠 캡처·초당 6프레임 전송, 로그아웃·오류 안내·미구현 메뉴, 재연결 로직.
- C: 로그인/조회 서비스 연결, 저장 결과 DTO 확정, 세션별 상태 머신 인스턴스 관리(다중 클라이언트 골격).
- 측정 결과에 따라 초기 설정값을 조정했다면 값·이유를 README에 기록.

완료 기준: 실제 웹캠 프레임이 서버까지 전달되어 ROI와 인원 안내가 클라이언트에 표시됨, 화면 이동 때 카메라 해제·세션 종료.

## 4. Day 3 — 자동 검사·상태 전이·다중 클라이언트
- A: 0.8초 안정 감지, 목표 2초·12프레임/최대 5초, 사람-PPE 연결.
- B: 대기/감지/분석 중/다중 인원 표시(서버 응답 기반), 서버 연결 끊김 안내.
- C: 취소·검사 세대·중복 실행 방지 통합, **TCP 연결 끊김 시 세션 정리**, 두 대 이상 클라이언트 동시 접속 테스트.
- 다중 인원 즉시 취소, 1초 이탈 취소, 단기 미검출 프레임 제외 확인.

완료 기준: ROI에 한 명이 서면 자동 검사, 인원 예외에서 누적값이 섞이지 않음, 클라이언트 2대 동시 접속 시 서로 간섭 없음.

## 5. Day 4 — 누적 결과·저장(MySQL)
- A: 최소 N/유효표/70% 규칙, Score=NULL, 대표 프레임·박스 이미지.
- B: 결과 3종, 판정 일치율, 재검사, 저장 진행/실패/재시도 표시(서버 응답 `SaveResultAck` 기반).
- C: 검사 1건+항목 3건+JPG 저장(MySQL 트랜잭션), 롤백·파일 정리, InspectionKey 중복 방지, ModelName/ModelVersion 저장.
- RESULT에서 Person 감지 유지, 저장 성공 후 이탈 자동 복귀 연결.

완료 기준: 실제 검사 결과가 MySQL에 저장, 재검사는 새 기록, 저장 재시도는 같은 검사 유지.

## 6. Day 5 — 이력·통계 완성
- 이력 최신순·50건 페이지·더블클릭 상세·누락 이미지 안내(서버 쿼리+응답).
- 전체/정상/점검 필요 카드와 미확인 보조 표시.
- 장비별 착용률, 결과 3종 비율, 최근 10건 실데이터.
- 0건 처리, 재검사 집계, 화면 진입 시 새로 조회.

완료 기준: 저장 결과가 이력과 대시보드에 일관되게 반영됨(클라이언트-서버 왕복 포함).

## 7. Day 6 — 구체적 오류·경계 검증
- 핵심 자동 테스트: `05_AI모델명세.md`의 판정 예제, 충돌 프레임, 경계 70%/50%, 최소 N.
- 상태 테스트: 다중 인원/이탈 취소, 재검사 조건, 시간 종료, 취소 후 늦은 결과 무시.
- 저장 테스트: 동일 InspectionKey 재시도 중복 없음, 항목 정확히 3개, 이미지 실패 시 롤백.
- 통계 테스트: UNKNOWN 포함 분모, 전체 합계, 0건 처리.
- **통신 테스트(신규)**: 길이 접두사 프레이밍 경계 조건(분할 전송·큰 프레임), 연결 끊김 시 세션 정리, 다중 클라이언트 동시 접속 부하.
- 실제 앱 확인: 모델 없음, 카메라 없음/분리, PPE 미검출, 저장 실패/재시도, 결과 중 감지, UI 응답성, **서버-클라이언트 연결 끊김/재연결**.
- 목업 변경 목록과 버튼 동작을 대조하고 범위 밖 기능은 추가하지 않는다.

완료 기준: 의미 있는 핵심 테스트 통과, 실제 웹캠 주요 예외 시연. 단순 화면 배치용 테스트를 늘리지 않는다.

## 8. Day 7 — 발표 검증·실행 안내
발표 흐름:
1. 서버 실행(MySQL 연결 확인) → 클라이언트 실행 → 로그인 → 대시보드.
2. 현장 검사 → 한 명 ROI 진입 → 자동 검사(클라이언트→서버 프레임 전송 확인).
3. 미착용이 실제 검출된 점검 필요 결과 확인.
4. 장비 착용 후 재검사 → 정상 결과 확인.
5. 작업자 이탈 → 대기 복귀 → 대시보드/이력 조회.
6. 미확인 또는 다중 인원 예외를 짧게 설명.
7. (선택) 클라이언트 2대 동시 접속 시연으로 다중 클라이언트 지원을 보여준다.

- 실제 검출이 미확인이면 결과를 강제로 바꾸지 않는다. 사전에 촬영 조건과 설정을 확인한다.
- Windows 최종 빌드(Client·Server)와 핵심 테스트, 실제 모델 연결, 오프라인 실행(로컬 MySQL 포함) 확인.
- 모델·runtime 준비, 초기 계정, MySQL 접속 정보(발표용), 저장 위치, 설정값·측정 결과, 알려진 한계를 README에 정리.
- 기존 사용자 DB를 초기화하지 않는다. 발표 준비용 새 데이터 경로를 사용하려면 별도 명시한다.

## 9. Git·통합
권장 브랜치: main / develop / feature/ai / feature/client / feature/server / feature/data.
매일 기능 단위로 통합하고 Client·Server 양쪽 빌드를 확인한다. models의 큰 파일과 런타임 DB/이미지는 소스 코드와 분리해 배포한다. Protocol 프로젝트 변경은 3명 모두에게 공지 후 병합한다.
