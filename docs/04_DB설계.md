# DB 설계서

문서 버전: 3.0 / 개정일: 2026-09-10
개정 사유: SQLite → MySQL 전환, 모델명·버전 컬럼 추가, 서버 단일 접근자 구조 반영.

## 1. 저장 위치·공통 규칙
- **MySQL 8.0** + EF Core, **Pomelo.EntityFrameworkCore.MySql** 프로바이더.
- DB는 서버와 같은 머신에 co-locate하는 것을 권장. 연결 문자열은 서버 설정 파일(`appsettings.json` 등)로 분리한다.
- 서버(SafetyVision.Server)만 DB에 접근한다. 클라이언트는 DB 커넥션 문자열을 갖지 않는다.
- 스키마 변경은 EF Core Code-First Migrations로 관리한다 (`SafetyVision.Data/Migrations`).
- 이미지 파일: 서버 실행 머신의 `%LocalAppData%\SafetyVision\snapshots\yyyyMMdd\inspection_{id}.jpg` (서버 기준 경로로 통일, 클라이언트에는 경로를 노출하지 않고 이미지 바이트만 전송).
- 서버 재실행 시 기존 DB·이미지를 삭제하지 않는다.
- 시각은 UTC ISO 8601 형식으로 저장하고 클라이언트 UI에서 로컬 시간으로 변환한다.
- 이미지의 yyyyMMdd는 검사 완료 시점의 로컬(서버) 날짜를 사용한다.
- INTEGER PK는 EF Core long, REAL/DECIMAL은 double 또는 decimal, nullable 항목은 nullable 형식으로 매핑한다. MySQL 예약어 충돌에 유의한다(예: `Score`는 문제 없음).

## 2. Users
| 컬럼 | 형식(MySQL) | 설명 |
|---|---|---|
| Id | BIGINT PK AUTO_INCREMENT | 계정 ID |
| LoginId | VARCHAR(64) UNIQUE NOT NULL | 로그인 ID |
| PasswordHash | VARCHAR(255) NOT NULL | 알고리즘·반복 횟수·salt·해시를 포함한 인코딩 문자열 |
| Name | VARCHAR(100) NOT NULL | 표시 이름 |
| CreatedAt | DATETIME(6) NOT NULL | UTC 생성 시각 |

- 최초 생성 시 admin / SafetyVision!2026 / 관리자 1계정 Seed(서버 시작 시 마이그레이션 이후 수행).
- PBKDF2-HMAC-SHA256, 반복 600,000회, 무작위 salt 16바이트, 출력 32바이트를 초기 구현값으로 사용한다.
- .NET 기본 암호화 API를 사용하고 검증은 고정 시간 비교로 수행한다. 비밀번호 평문·로그 기록 금지. TCP 전송 구간에서도 평문 로깅 금지.
- 계정이 이미 있으면 비밀번호를 재설정하거나 계정을 중복 생성하지 않는다.

## 3. Inspections
| 컬럼 | 형식(MySQL) | 설명 |
|---|---|---|
| Id | BIGINT PK AUTO_INCREMENT | 화면 No·파일명에 쓰는 DB 번호 |
| InspectionKey | CHAR(36) UNIQUE NOT NULL | 검사 시작 시 생성한 GUID, 저장 재시도 중복 방지 |
| InspectedAt | DATETIME(6) NOT NULL | UTC 검사 완료 시각 |
| Result | VARCHAR(20) NOT NULL | NORMAL / CHECK_REQUIRED / UNCONFIRMED |
| PersonConfidence | DOUBLE NULL | 대표 프레임의 대상 Person confidence, 0~1 |
| ImagePath | VARCHAR(255) NOT NULL | 서버 데이터 루트 기준 이미지 상대 경로 |
| **ModelName** | VARCHAR(100) NOT NULL | 판정에 사용한 모델 저장소명 (신규) |
| **ModelVersion** | VARCHAR(50) NOT NULL | 판정에 사용한 모델 버전 (신규, 예: `v2`) |
| CreatedAt | DATETIME(6) NOT NULL | UTC 저장 레코드 생성 시각 |

- InspectionKey는 기존 정수 PK를 유지하면서 재시도를 같은 검사로 식별하기 위한 추가 필드다.
- 신규 검사·재검사마다 새 InspectionKey. 저장 재시도는 기존 키를 재사용한다.
- 실패로 롤백된 시도의 DB 번호는 달라질 수 있다. 논리적 검사 동일성은 InspectionKey로 보장한다.
- Result 허용값은 CHECK 제약 또는 애플리케이션 레벨 검증으로 보장한다(MySQL은 네이티브 ENUM 또는 CHECK 제약 사용 가능). InspectionKey UNIQUE, `(InspectedAt, Id)` 조회 인덱스를 둔다.
- ModelName/ModelVersion은 검사 시점에 서버가 로드한 모델 정보를 그대로 기록하며, 이후 모델이 바뀌어도 과거 기록은 변경하지 않는다.

## 4. InspectionItems
| 컬럼 | 형식(MySQL) | 설명 |
|---|---|---|
| Id | BIGINT PK AUTO_INCREMENT | 항목 ID |
| InspectionId | BIGINT NOT NULL | Inspections.Id FK |
| EquipmentCode | VARCHAR(20) NOT NULL | hardhat / vest / mask |
| Status | VARCHAR(20) NOT NULL | WORN / NOT_WORN / UNKNOWN |
| Score | DOUBLE NULL | 판정 일치율 0~1, UNKNOWN이면 NULL |
| PositiveFrames | INT NOT NULL | 착용 단독 검출 프레임 수 P |
| NegativeFrames | INT NOT NULL | 미착용 단독 검출 프레임 수 M |
| TotalFrames | INT NOT NULL | 대상 Person이 인원·크기 조건을 충족한 분석 프레임 수 N |
| CreatedAt | DATETIME(6) NOT NULL | UTC 생성 시각 |

- `UNIQUE(InspectionId, EquipmentCode)` 및 FK(`ON DELETE CASCADE` 또는 애플리케이션 트랜잭션으로 일관성 보장)를 실제 DB 제약으로 적용한다.
- EquipmentCode·Status 허용값, 표수 0 이상, `P+M <= N`, Score 0~1 또는 NULL을 검증한다.
- UNKNOWN이면 Score=NULL, 나머지는 Score NOT NULL인 규칙을 검증한다.
- 저장 서비스가 검사마다 hardhat/vest/mask 정확히 3건임을 보장한다.
- 3개 항목의 N은 같고, N-P-M은 충돌 또는 미검출 프레임 수다.
- 대표 Person confidence와 장비 Score는 서로 다른 의미다.

## 5. 관계
Inspections 1건에 InspectionItems가 정확히 3건 연결된다. FK는 InspectionItems.InspectionId → Inspections.Id이다.
검사와 항목은 서버 내 하나의 MySQL 트랜잭션으로 저장한다. 사용자와 검사 작업자를 연결하지 않는다. 얼굴·신원 인식은 범위 밖이다.
AI 추론(ONNX)은 이 트랜잭션 밖에서 수행하고, 완료된 판정 결과 DTO만 트랜잭션 안으로 전달한다(설계 요구사항: AI는 업무 데이터를 직접 변경하지 않음).

## 6. 대표 이미지
- 장비 중 착용/미착용 한쪽만 검출된 장비 종류가 가장 많은 프레임을 선택한다. 동률은 더 나중 프레임.
- 그 프레임의 실제 대상 Person/PPE 박스와 클래스명만 그린다. 가상의 박스나 다른 프레임의 박스를 합성하지 않는다.
- JPG 품질 90. 이미지 자체에 박스를 그리므로 박스 좌표 테이블은 만들지 않는다.
- N=0으로 시간 종료하면 마지막으로 확보한 카메라 프레임을 사용하고 PPE 박스를 그리지 않는다. 캡처 자체가 실패하면 장치 오류로 취소한다.
- 이미지 파일은 서버가 저장하고, 결과 화면 요청 시 서버가 파일을 읽어 TCP로 바이트를 전송한다(클라이언트는 파일 경로를 직접 알 필요 없음).

## 7. 저장 절차·실패·재시도
DB와 파일시스템은 단일 원자 트랜잭션이 아니므로 다음 보상 처리를 서버가 구현한다.
1. 완료 결과 DTO와 대표 프레임을 서버 메모리에 고정하고 InspectionKey별 동시 저장을 잠근다.
2. 해당 InspectionKey의 기존 정상 저장 기록을 먼저 조회한다. 있으면 새 INSERT 없이 기존 결과를 사용한다.
3. JPG를 같은 날짜 폴더의 임시 파일에 쓴다. 실패하면 INSERT하지 않는다.
4. MySQL 트랜잭션에서 검사·항목 3개(+ModelName/ModelVersion)를 저장하여 Id를 얻고 최종 ImagePath를 설정한다.
5. 임시 파일을 최종 파일명으로 이동한 뒤 DB를 커밋한다. 모두 성공하면 클라이언트에 저장 완료를 응답한다.
6. 실패하면 커밋 여부를 확인한다. 커밋된 정상 기록의 이미지는 삭제하지 않는다. 미커밋이면 롤백하고 이번 시도 파일을 정리한다. 클라이언트에는 `SAVE_FAILED`를 응답한다.
7. 저장 실패 결과는 서버 메모리에 유지한다. 저장 재시도 요청은 같은 InspectionKey·시각·판정·이미지로 위 절차를 다시 수행한다.

- 이미지 누락이 발견된 같은 키의 기존 기록은 보유한 대표 프레임으로 이미지를 복구하고 행을 추가하지 않는다.
- 저장 진행 중 화면 이동·재검사 요청은 서버가 거부하고 작업을 중복 실행하지 않는다.
- 저장 실패 중 자동 대기 복귀·재검사는 잠근다. 클라이언트는 저장 재시도 또는 미저장 결과를 버리고 대시보드 복귀 요청 가능.
- 서버 비정상 종료 시 미저장 메모리 결과는 복구하지 않는다. 다음 서버 실행 시 DB 연결이 성공한 뒤, 임시 파일과 DB가 참조하지 않는 서버 소유 이미지 파일을 정리한다. DB 연결 실패 시 파일 정리를 하지 않고, 서버는 클라이언트 연결 자체를 거부한다(신규).
- DB가 참조하는 이미지가 없으면 해당 기록을 삭제하지 않고 이력 화면에서 누락 안내한다.
- MySQL은 여러 클라이언트 세션이 각자 다른 InspectionKey로 동시에 쓰기 때문에 기본 격리 수준(READ COMMITTED, InnoDB 기본)으로 충분하며 별도의 애플리케이션 레벨 락 설계는 필요하지 않다. InspectionKey UNIQUE 제약이 중복 삽입을 최종 방어한다.

## 8. 통계·이력
모든 집계는 저장에 성공한 전체 기간의 기록 기준이며, 서버가 MySQL 쿼리로 계산해 클라이언트에 응답한다.

| 항목 | 정의 |
|---|---|
| 전체 | COUNT(Inspections) |
| 정상 | Result=NORMAL 건수 |
| 점검 필요 | Result=CHECK_REQUIRED 건수 |
| 미확인 | Result=UNCONFIRMED 건수 |
| 결과 비율 | 각 결과 건수 / 전체 검사 건수 |
| 장비별 착용률 | 해당 EquipmentCode의 WORN 건수 / 해당 EquipmentCode의 전체 항목 수 |
| 최근 검사 | InspectedAt DESC, Id DESC, 10건 |
| 검사 이력 | 동일 정렬, 페이지당 50건, OFFSET/LIMIT (조건 검색 파라미터 지원) |

- 착용률 분모에 NOT_WORN과 UNKNOWN을 모두 포함한다.
- 검사 1건당 장비 3건이므로 각 장비의 분모는 전체 검사 건수와 같아야 한다.
- 전체=정상+점검 필요+미확인. 재검사는 별도 검사이므로 집계에 포함한다.
- 백분율은 화면에서 정수로 반올림한다. 반올림된 비율의 합은 100과 약간 다를 수 있다.
- 0건이면 비율 계산을 하지 않고 서버 응답에 `null`/`—` 표시 플래그를 담아 클라이언트가 `검사 기록이 없습니다.`를 표시한다.
- 저장된 장비 Score를 평균내서 착용률로 사용하지 않는다.
